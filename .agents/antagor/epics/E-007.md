## Problem

To add the columns of one table to another by a key (VLOOKUP), a user exports both to Excel or writes pandas or SQL by hand. dataio stacks many sources into one, but it cannot match the rows of different sources by key columns, and query= sees one table only.

## Goal

dataio join main.csv out.xlsx --lookup prices.xlsx#Prices --on sku (and join() in the library) writes the main table with the lookup's columns matched by the named keys (left, right, inner or full; one key or several) to any target, with a report of how many rows found a match.

## Acceptance (Given–When–Then)

- Given a main source and a lookup with a common key column, When dataio join runs with --on KEY and no --how, Then the join is left: every main row stays, in its order, with the lookup's columns, empty where nothing matched, and the report gives for the lookup the main rows matched and not matched
- Given --on phrase --on region, When dataio join runs, Then a row matches only when both keys are equal
- Given key columns with different names, When --on sku=article, Then sku of the main source matches article of the lookup and the result has one key column, sku
- Given no --on, When dataio join runs, Then it is refused with INVALID_ARGUMENTS (exit 2): keys are never taken from same-named columns
- Given a key column that a source does not have, When dataio join runs, Then it is refused with INVALID_ARGUMENTS naming the source, the column and the source's columns, and nothing is written
- Given --how inner, right or full, When dataio join runs, Then the result has the matched rows only, every lookup row, or every row of both, and the key column takes its value from the side that has it
- Given two lookups, When --lookup a --lookup b with left, inner or full, Then each is joined to the main source in the given order; with --how right and more than one lookup the run is refused with INVALID_ARGUMENTS
- Given the key 123 (a number) on one side and '123' or ' 123 ' (text) on the other, When dataio join runs, Then they match (compared as text, outer spaces trimmed), while 'A'/'a' and 'Ёлка'/'Елка' do not, and the key column keeps the main source's type
- Given an empty key cell, When dataio join runs, Then it matches nothing: with left the row stays with empty lookup columns, and the report counts these rows
- Given a key repeated in a lookup, When dataio join runs, Then a main row gets every match (rows are added) and the report warns, naming the first repeated keys and the number of rows added
- Given a non-key column with the same name in the main source and a lookup, When dataio join runs, Then the main column keeps its name and the lookup's gets the suffix _<lookup name> (the part name of its address, else the file stem), and --columns/--rename choose and name the target columns as in convert
- Given any target convert takes (a file, a part, a base table, a Google sheet, stdout -), When dataio join writes, Then write modes, backups (dataio restore brings a replaced target back), the refusal to write over a source without --overwrite, and --dry-run (the report with the match counts, nothing written) work as in convert
- Given two joins writing the same target at once, When they run, Then each write is the same as a convert write to that target (atomic file replace, one transaction for a base): join adds no write path of its own
- Given the library, When join(source, target, lookups=[...], on=[...], how=...) runs, Then it returns the report of the CLI, every keyword is a flag of the same name (ADR 0001), and the sources may be Python objects
- Given dataio describe, dataio join --help and the skill, When an agent reads them, Then join is described with an example of a left join by two keys

## Implementation decisions

- Public API join(source, target, *, lookups, on, how='left', the read options of convert with in_ (they apply to every source), the write options of convert with out_ and columns/rename/mode/backup/overwrite/dry_run) -> Report; CLI command dataio join SOURCE TARGET --lookup ADDRESS (repeatable) --on KEY (repeatable) --how left|right|inner|full
- on: a list of items, each a column name or main_name=lookup_name; how: an enum left|right|inner|full, default left
- A core join module: reads the main source and each lookup through the existing read path, joins in DuckDB over the frames (ADR 0002, 0003), compares keys as trimmed text and keeps the main key's type, writes through the existing write path of convert
- Report: a new list lookups, one entry per lookup with its address, rows, matched, unmatched and empty_keys; repeated keys go to warnings; the --json shape is pinned by tests

## Test seams

- The library join() (ADR 0001: the library and the CLI are equal): the returned report, and the written target read back with read()
- The CLI dataio join ... --json through CliRunner (invoke_json), and the parity test of ADR 0001 (every keyword of join() is a flag of dataio join)

## Out of scope

- anti join (rows without a match) and a first-match mode like VLOOKUP's
- key normalisation (case, ё, norm_phrase) and fuzzy matching
- keys or a kind per lookup, and a lookup joined to another lookup: every lookup joins the main source by the same keys
- SQL over several sources (query= with several tables), and query= in join
- an in-memory result (join with no target)
- streaming: the data is loaded whole, as everywhere in dataio
